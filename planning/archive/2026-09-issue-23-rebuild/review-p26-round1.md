## Findings

- **[severity: bug]** scripts/03_cog.py:223-249 (`main`), scripts/05_stac_register.py:240-251 — 03 turns **every** GeoTIFF under `data/raw/georef/thumbs/` into a COG if its stem has a row in **any** window parquet. A window holds the whole fetch window (1,013 rows on se_c), not the selected set, and 03 never reads the georef manifest. So a GeoTIFF that 02 did not produce for the current inputs still gets tagged with the current run's `ROTATION`, `ROTATION_SOURCE`, `FLY_SHA` and `PIPELINE_SHA`. 05 then registers it with the same properties from the same window row, and `stac_validate.py` passes it, because tag and property come from one source. 02's manifest staleness check only reaches `fr`, meaning frames that are selected **and** fetched. It never reaches:
  - a GeoTIFF left from an earlier run whose frame is no longer selected. A fly upgrade, a DEM or catalogue refresh, or a new `no_bearing` / `footprint_misses_aoi` outcome all deselect frames. That raster was written by the old fly or the old rotation, and it ships stamped with the new `nge:fly_sha` and `airphoto:rotation`;
  - running 01 (with a changed `rotation_roll.csv`) and then 03 without re-running 02. The new rotation tag goes onto the old-rotation raster;
  - an orphan COG in `data/stac/thumbs/` whose GeoTIFF 02 deleted as stale and then failed to regenerate. 03 does not remove it, and 05 registers it. It is caught only if one of the tagged build fields changed. A bearing-only change passes.

  **Probe (scratch copy, `cc-r1/w`):** I copied a real GeoTIFF to `data/raw/georef/thumbs/1967/bc5255_193_thumb.tif`. Its frame is airp_id 1259554, which the se_c ledger records as `footprint_misses_aoi`, and it has no manifest row. Result: 03 wrote `1 COGs written`, 05 wrote `1 items + collection valid`, and stac_validate reported `1 of 1 items pass`. The item carries `nge:fly_sha 988d1b18e654`, `airphoto:rotation 0`, `rotation_source assumed_by_series`. The provenance guarantee #30 exists to give is false for such a frame, and nothing flags it. `--require-all-published` checks only for missing items, not extra ones.

  Fix direction: 03 should COG only GeoTIFFs whose manifest row matches the window's rotation and the run's `fly_sha` (and refuse or skip the rest). It should also drop or refuse COGs with no current GeoTIFF. Alternatively, 05 should register only ids that are `selected` in some ledger.

- **[severity: fragile]** scripts/02_georef.R:138-152 — the manifest decides whether an existing GeoTIFF is reused on three keys only: `rotation`, `footprint_bearing` and `fly_sha`. None of these captures the footprint's **size or position**. The other inputs are the DEM (`aoi_dem(id)`; 01's own remedy for a shortfall says to delete the DEM and raise `aoi_dem_corner()`) and the catalogue's `scale`, `flying_height`, `focal_length` and centroid after a `FORCE_REFRESH` re-query. If any of those changes a frame's footprint and leaves its bearing alone, `fly_georef(overwrite = FALSE)` silently reuses the GeoTIFF sized under the old inputs. The raster then disagrees with the footprint that selected it, and with the `height_source` / `footprint_basis` it is tagged with. Suggest recording a digest of the footprint ring from `fp`, which 02 already computes, in place of or beside the bearing.

- **[severity: fragile]** scripts/04_s3_upload.R:104-117 — the head-object spot check assumes `ChecksumSHA256` is a full-object digest. For an object that `aws s3 sync` sends as a multipart upload (above the CLI's default 8 MB threshold), S3 returns a composite checksum-of-parts (`...-N`). `base64_dec` of that either errors or produces a mismatch, so `04` stops **after** the sync has already published, with a message blaming the object. The largest se_c COG is 5.7 MB, so this is latent. It fires the first time a sampled COG crosses 8 MB (a large RGBA frame or a scan). The local CLI (aws-cli 2.34.34) documents this caveat in `head-object help`. Either skip or strip a `-N` composite value, or raise `multipart_threshold` for the sync.
